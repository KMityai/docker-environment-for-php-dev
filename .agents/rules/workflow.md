# Правила работы агента в проекте

Общие правила для любого агента, который меняет этот репозиторий
(Docker-окружение для запуска произвольных программ на чистом PHP).
Специализированные инструкции лежат в `.agents/skills/`:

- `.agents/skills/php-84/SKILL.md` — стандарты кода чистого PHP 8.4;
- `.agents/skills/docker-php/SKILL.md` — работа с Docker-окружением проекта.

## 1. План перед правками

- Перед любым изменением **более одного файла** составь краткий нумерованный план:
  что меняется, в каком файле и зачем. План выводится до внесения правок и
  служит чек-листом для самопроверки.
- Перед правкой одного файла достаточно одной строки: файл + суть изменения.
- Если по ходу работы выяснилось, что план неверен — обнови план явно, а не
  правь «по инерции».
- Изучай реальную конфигурацию (`Dockerfile`, `docker-compose.yaml`,
  `docker/php/php.ini`) перед выводами: имена сервисов, версии и пути берутся
  из файлов, а не из общих знаний.

## 2. Ограничение повторов неудачных исправлений

- Одно и то же исправление запрещено повторять **более двух раз**
  (две неудачные попытки — предел).
- После второй неудачи: остановись, кратко опиши, почему подход не работает,
  и предложи **2–3 принципиально разных решения** с плюсами/минусами, затем
  дождись выбора.
- «Принципиально иное» — это не косметика (порядок строк, переименование флага),
  а другая стратегия: другой образ, другой механизм Composer, downgrade версии,
  отказ от патча в пользу конфигурации и т.п.
- Повторное выполнение одной и той же команды с тем же результатом — тоже
  повтор; не «долби» сломанную сборку, а диагностируй причину
  (`docker compose config`, `docker build --progress=plain`, логи).

## 3. Git

- Вся работа ведётся **в отдельной ветке** от актуальной ветки
  (например `feat/php-84-and-agent-skills`); прямые коммиты в `master` запрещены.
- Коммит делается после каждого **завершённого логического этапа** — один коммит
  на одну цель; смешивать обновление образа и правку compose нельзя.
- Сообщения коммитов — **Conventional Commits** на английском:
  `chore(agents): ...`, `build(docker): ...`, `chore(docker): ...`,
  `feat: ...`, `fix: ...`, `docs: ...`.
- Перед первым изменением проверь `git status`: чужие незакоммиченные правки
  **не включай** в свои коммиты и предупреди о них.
- Добавляй в индекс файлы **явно по путям** (`git add .agents/`,
  `git add Dockerfile`), а не `git add -A` / `git add .`.
- **Никогда** не коммить:
  - секреты и переменные окружения: `.env`, `.env.*` (кроме `.env.example`);
  - временные файлы: `*.tmp`, `*.bak`, `*.log`, дампы, одноразовые скрипты;
  - артефакты сборки: `vendor/`, `composer.lock`, `composer-home/`, `build/`;
  - локальные IDE-настройки (`.vscode/*`).
- Не переписывай историю опубликованных веток (`rebase`, `amend`, `push -f`)
  без явного запроса пользователя.

## 4. Обязательный цикл самопроверки (Verification Loop)

После каждой группы изменений выполни проверки и только потом коммить.
Приоритет — внутри Docker-контейнера, чтобы результат соответствовал CI/окружению.

```bash
# 0. Окружение собрано и поднято
docker compose -f docker-compose.yaml up -d --build

# 1. Синтаксис каждого изменённого PHP-файла
docker compose -f docker-compose.yaml run --rm php php -l path/to/file.php

# 2. Стиль и статический анализ (если установлены в образе/проекте)
docker compose -f docker-compose.yaml run --rm php php-cs-fixer fix --dry-run --diff
docker compose -f docker-compose.yaml run --rm php phpstan analyse -l max

# 3. Валидация compose-файла (обязательно после любой правки compose)
docker compose -f docker-compose.yaml config --quiet
```

- Если контейнер недоступен, те же проверки выполняются локально теми же
  командами (`php -l`, `php-cs-fixer`, `phpstan`, `docker compose config`),
  и это отражается в отчёте.
- Не отчитывайся об успехе, не показав вывод проверок. «Должно работать» —
  не результат; результат — код возврата `0` и вывод команды.
- Проверки входят в Definition of Done: без них этап не считается завершённым.
